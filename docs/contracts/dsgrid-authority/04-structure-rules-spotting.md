# 04 — Structure rules, computed capacities and optimum spotting

Data: `standards/reg-mv-structure-rules.v1.json` (REG Distribution Reticulation Standard v7, Aug 2025; Transmission Ed.1 for HV) including the owner's **reservations** block. This contract binds how the engine uses it.

## Observed today

- Structure types imported from PLS carry `unresolved_binding` on pole strength ("native pole strength scalars are explicitly uncharacterized and never create capacity or a support-method claim"); the PLS-POLE inputs (`.012/.014/.POL`, v22) and `default.wpp` are pass-through only. So `plan_optimum_spotting` ("clearance- and structure-capacity-constrained") has no capacity to constrain on.
- What PLS-CADD checks today are the **typed** Method-1 allowables in the `.str` files (structure #230 `j-w-60d-S190.012`: max wind 200 m, max weight 500 m, min weight −1500 m, max angle 79.9998°, identical for every load case) — the consultant's point 2.
- The engine has `screen_structure_usage`, `calculate_stringing_and_structures`, `compute_support_demands`, `run_structure_analysis`, weight-span cases (`minimum_weight`, `maximum_weight_slot`, `maximum_wind`, `insulator_swing`, `interaction_diagram`, `detailed_structure`).
- Nyamagabe structure-type naming encodes the family: `a-w / b-w / d-w / e-w / ex- / j-w / l-w / l-s / m-c` (letter type; w = wooden, s = steel, c = concrete), `-60d/-120d` (angle class), `-stay`, `-susp`, `-longspan`, `-toff`, `-S140/-S190/-S255/-S325` (class), `.012/.014` (12 / 14 m), `NPD850/1000/1250` (concrete pole class).

## Required

1. **Rules as checks**, from the JSON, on every `analyse usage` / `spotting plan` receipt, each with station, structure, rule id, source clause and a *reason* slot:
   - span vs Table 15 (pole height × material × conductor) and the design span (65 m wooden / 70 m other);
   - **reservation**: a span above the heuristic is `above_heuristic_justified` when a feature code / obstacle in the span justifies it and a special structure is used (14 m, steel, H-pole, H-pole long-span with stays, three-pole), up to 150 m; > 150 m → `needs_design_decision` (contract 07); never "violation";
   - strong pole (concrete/steel) after ≤ 5 wooden poles; strain structure every ≤ 5 spans; strong structure every ≤ 10 spans — with a reason slot ("would land in swamp / unbuildable");
   - tap first span from a single wooden pole ≤ 25 m; earth wire earthed ≤ 400 m;
   - angle pole class: supported angle = MV medium, unsupported = MV stout; single pole 10°–60° is *not approved* (EDCL drawing -04) → H-pole (-11) or -05 per the project's approved principle;
     *Landed 2026-09-20 (`program/01b-d12`, engine `ds_grid_engine::structure_rules`):* the issued JSON carries the angle-pole classes (Table 4) but **no angle band**, so the band is declared in code as rule `mv.angle_pole_class.single_pole_not_approved_band` = `10° ≤ |line angle| < 60°` with source clause "EDCL drawing set 215-W045S-A0101 sheet -04 'Not recommended', D2 1.6; REG v7 §1.6.2", and every receipt lists it under `assumptions` with `assumed: true` — the standard was not edited. *Decisions:* the rule applies to every single-pole family (a, b, d, e, l) whatever the material (the consultant's own example #68 is a steel `l-s-stay.012`); 60° and above is the -05 band and raises nothing; the family is read from the type name by a pure tested grammar (`a/b/d/e/l` single, `j` H-pole, `m` transformer, `ex` tapping; `w/s/c`; `-60d/-120d`; `-stay/-2stay/-susp/-longspan/-toff`; `S140…S325`, `S800`/`s800`, `NPD…`; `.012/.014`; `_Revised` kept as an unrecognised tag), never from the .str bytes. Line angle = change of route bearing at the structure from the model's own alignment geometry (vertex within 0.05 m), right turn positive as PLS-CADD prints it; on the Nyamagabe import all 110 native line angles matched to < 1e-3°, and the native value is printed beside it as `line_angle_source_deg`. The finding carries station, structure, rule id, source clause, current type, line angle, the allowed families (H-pole -11 / -05 at 60°–90°), `reason: null` (the engine invents no reason) and `assumed: true`. Nyamagabe today: 26 single poles in the band; #230 (`j-w-60d-S190.012`, 51.35°) is an H-pole by its own library description and raises nothing; #68 (`l-s-stay.012`) is at 78.09°, outside the contracted band.
   - foundation depth/width by pole height (Table 14) in the structure list.
2. **Wind span and weight span, always both**, per load case, with definitions printed in the receipt header (wind span = ½ Σ adjacent horizontal spans; weight span = distance between adjacent low points, per weather case, negative = uplift). The governing one is named. The client confuses them; the receipt does not let them.
3. **Capacities computed, not typed**: read PLS-POLE 22 inputs and `default.wpp` (wood pole dimensions/strength) into structure-type capacities; where the pole GTP is missing, accept a declared REG Table 4 class (`--pole-class "MV stout 12 m"`) as an explicit, labelled assumption; derive allowable wind span, weight span max/min and max line angle per structure type, pole height and load case; write them back to the `.str` files on sync (contract 02) so PLS-CADD checks the same numbers.
4. **Optimum spotting**: `ds dsgrid spotting plan --model … --alignment … [--from-clearance-report] [--objective cost|count|clearance] [--allow-types <list>] [--max-span 150]` proposes re-spotting / taller pole / structure-type change per violation with the BOQ delta (poles by class, stays, cross-arms, insulators, OPGW sets from the assembly BOMs); `spotting apply --plan <id> --yes` applies it as one revision. Special structures available to the planner: 14 m poles, steel poles, H-pole (-11), H-pole long-span with **2 stays** (the only stayed long-span modelled today — more stays require a new structure type, contract 05), three-pole with long cross-arm.
5. **Structure list / staking table** export with description, station, angle, pole height/material/class, assembly drawing number, stays, foundation, rule findings and reasons — the consultant's point 1 in one command (`ds dsgrid report structures --model … --out …xlsx|csv`).
   *Landed 2026-09-20:* columns `structure_id, number, alignment_id, station_m, line_angle_deg, line_angle_source_deg, structure_type, description, type_description, family, pole_count, material, pole_height_m, pole_class, stays, angle_class_deg, assembly_drawing, foundation_depth_m, foundation_width_m, findings, finding_rules, allowed_families, reasons, x_m, y_m`; `description` is the placed structure's own (`structure describe`), `type_description` the library's; the assembly drawing number is read from the description or the type's description when it carries a `W045S-A0101-NN`-shaped token; foundation depth/width from Table 14 by the pole height in the type name (12 m → 1.8/1.0, 14 m → 2.2/1.0; blank when the name carries no height). CSV with a UTF-8 BOM; XLSX through the shared `ds-io` writer (adds a `geometry_wkt` point column). Rows in the receipt are bounded by `--limit` with `more.withheld`; the file is whole. `verification_level: proposal` and the standard's `{schema, version, issued, digest}` on every receipt. Columns for the D4 findings (spans, sequence, tapping, earthing) are the same `findings/finding_rules/reasons` cells; they fill when 04 §1–3 land.
6. **Verification level** on every strength/spotting receipt (contract 06): `proposal | verified_within_tolerance | authority`.

## Refusals

`capacity_unknown` (structure type without capacity and no declared class — spotting cannot constrain), `span_over_150_needs_decision`, `structure_type_not_allowed` (single pole in 10°–60°), `rule_source_missing` (JSON digest mismatch).

*Landed 2026-09-20:* `structure_type_not_allowed` is raised by `dsgrid structure retype --yes` when the write would leave or create the state (the dry run reports it as `refusal_on_write` and a warning); `rule_source_missing` when the vendored copy of `reg-mv-structure-rules.v1.json` (crates/ds-grid-engine/standards/, `-text` under git so the issued CRLF bytes stay exact) does not hash to the pinned `9a43f7f5…`.

## Acceptance

```
ds dsgrid analyse usage --model local-… --output json        → per structure: wind span + weight span per case, allowables computed (or 'declared class' flag), rule findings with reasons
ds dsgrid analyse usage … | jq '.findings[] | select(.rule=="span_table15")'   → spans > heuristic show 'above_heuristic_justified: SWAMP|RIVER_EDGE|…' where a code justifies them
ds dsgrid spotting plan --model local-… --alignment aln-…-29 --from-clearance-report --max-span 150 --output json  → proposals with BOQ delta
ds dsgrid spotting apply --plan <id> --yes ; ds dsgrid analyse clearance --model local-… → violations on that alignment 0
ds dsgrid report structures --model local-… --out structures.xlsx
```
