# 03 — Feature codes and clearance across the boundary

Standard: `standards/PLS-FEATURE-CODE-STANDARD-v1.md` (+ `pls-feature-codes.v1.json`, owner-issued, 60 codes, ground = 200, unknown = 999, clearances per voltage class LV / MV / HV_110 / HV_220, description schema per code, 376 aliases). Its §7 lists P1–P9; this contract is their binding form.

## Observed today (receipts of 2026-09-20)

- `feature_code_report` on every PLS-imported model: `resolved: {}`, `usage: {}`; 77 unresolved tokens in Nyamagabe (Gp 2778, Forest 499, Road 378, Swamp 201 + SWAMP 6, Angle Point 193, River 63, transformer names 41, Tap/TapN 26, T-Off 8, LIGN 1); Gisagara and Model 2: only `other` (1357 / 4030) — descriptions lost before or at import.
- `project_criteria_workbench`: `clearance_rules: []` in every model; the workspace `.cri` has `clearance_voltage 0`; the `.fea` has 10 codes, RV 6 m (8 m road), **RH 0 m everywhere**; TIN/terrain default code 200.
- Weather sets differ within one project (Model 1: high wind 25 °C / 551.7 Pa, max conductor 60 °C; Model 2: 50 °C / 980.8 Pa, 75 °C). REG rates conductors at **75 °C**.
- The engine already has `author_feature_code / update / retire / delete`, `feature_code_report`, `author_criterion_rule`, `author_criterion_case_binding`, and the criteria option `minimum_vertical_clearance_m`, `display_clearance` role.

## Required

1. **FEA 15 import** (`dsgrid-exchange convert` and `pull`): code number, description, plan/profile symbol, RV, RH, ground/obstacle/side-profile kind, default terrain and TIN codes → `feature_code` definitions in the package; XYZ point descriptions resolved to codes; unresolved tokens reported by name and count. Receipt names `FEA 15`.
2. **Standard import**: `ds dsgrid feature-codes import --model … --standard pls-feature-codes.v1.json --voltage-class MV|LV|HV_110|HV_220 --yes` loads the 60 codes with the class's RV/RH (assumed values flagged), replacing or merging (`--merge`) with the model's table; `report` shows codes, RV/RH, TIN flag, usage, unresolved.
3. **Migrate**: `ds dsgrid feature-codes migrate --model … --standard … [--proposals <llm-accepted.json>] [--dry-run] --yes` — normalise → alias → heuristics exactly as `standards/tools/classify_feature_tokens.py`; legacy code map (Nyamagabe 1→1, 2→2, 3→3, 4→20, 5→51, 6→30, 7→22, 8→200, 9→4, 200→200); trailing numbers and `(NNkva)` become description fields; residue → 999 with the raw token in the description; receipt = mapping table + counts per code + list of 999s. `--deliver` refuses while any 999 remains.
4. **Export**: `ds dsgrid feature-codes export --model … --voltage-class MV --out <file.fea>` writes FEA 15 (symbols from the JSON); `sync` (contract 02) writes it into the linked workspace when the table changed.
5. **Clearance criteria**: `ds dsgrid criteria clearance set --model … --voltage-class MV --vertical-case "<weather label>" --horizontal-case "<weather label>" [--voltage-kv 30] --yes` fills `clearance_rules` (voltage, survey-point clearance cases, wire clearance line) from the class; CRI 94 read on import and written on sync (`clearance_voltage` never 0). `criteria show` lists rules; a project-wide `criteria compare` flags models whose weather sets or max conductor temperature (≠ 75 °C) differ.
6. **Clearance report**: `ds dsgrid analyse clearance --model … [--alignment …] [--case vertical|horizontal|both] [--limit]` — for every span and every terrain/feature point within the span corridor: feature code, RV/RH required (class table, obstacle height h applied), available at the governing case (vertical: max conductor temperature final; horizontal: high wind blow-out), deficit, violation flag, station, offset; per-alignment and per-code totals; obstacles with default h flagged; assumed clearances flagged. Same definitions as PLS-CADD's Terrain › Clearances so the two can be compared (contract 06 verifies).
7. **Survey app**: DS Field form template generated from the JSON (labels en/fr/rw, code, fields with types/enums/required, rendered description); XYZ 5 export with code + description; the point round-trips app → XYZ → PLS-CADD → DS Grid with fields intact. *Deferred (03-d3, 2026-09-20): not in the delivery cut; nothing landed.*
8. **Skills**: `ds-pls-feature-codes` and `ds-mv-clearance-setup` (drafts in `gaps/skills-drafts/`) enter the bundle once 2–6 exist. *Deferred (03-d3): the supervisor's call now that 2–6 exist.*

## Decisions taken while landing (03-d3, 2026-09-20)

Where this contract was silent or could not be honoured as written, the smallest behaviour consistent with the `dsgrid` / `pls` contracts was taken and is recorded here.

1. **Feature-code identity in the model.** A definition's invariant `code_token` is its NAME (the standard's `GROUND`, `ROAD_PUBLIC` … or the FEA member's own description for an imported legacy table); the PLS-CADD number lives in `clearance.code_number`. A legacy and a standard definition sharing a name are one feature (legacy `SWAMP` 4 becomes standard `SWAMP` 20 on import, in place); the rest are joined by the legacy code map on migration. Standard definitions carry `namespace = ds.pls-feature-codes/v1@<version>`.
2. **Standard digest.** The JSON carries no digest, so the build pins the SHA-256 of each issued version's bytes (line endings folded to `\n`, because a checkout converts them and that is not an edit). `--standard <path>` naming a pinned version with other bytes is `standard_digest_mismatch`; a version the build does not pin is accepted and flagged `standard_unpinned` in every receipt (the owner issues new versions faster than builds). `--standard pls-feature-codes.v1.json` (the owner's name) resolves to the bundled bytes without a path.
3. **FEA 15 columns not characterized** (the two values after the header, the six per-code header flags, the second value pair, the INLINEDATA symbol lines) are carried verbatim on import and rewritten byte for byte; a code the model authored gets the field file's flag pattern for its kind (ground `0 0 2 0 0 0`, other `0 0 2 1 1 0`), the pair `0 0`, and a symbol by numbering band. The owner verifies the Feature Code Data dialog columns once.
4. **TIN membership on FEA import** is not in the member: it is the default terrain/TIN code, plus what the standard's legacy map says for the mapped code; everything else imports as a non-ground point without a default height.
5. **Migration input.** A point on a legacy FEA definition (a `code_number` and no voltage class) is joined by the legacy map and its survey text only supplies fields; a disagreement between the text's classification and the map is listed, the map wins. Any other point's class token is classified exactly as `classify_feature_tokens.py` (2,507-token equivalence check, zero differences). An UNKNOWN point keeps its raw token verbatim as its description and is classified again on the next pass (`--proposals` = accepted `{token, code}` rows applied as exact aliases). Breakline and crossing tokens are not migrated (listed as untouched). The description of a migrated point is the code's template rendered from the fields.
6. **`--voltage-class` on migrate** is optional: the class the table already carries (from `import`), MV when the table carries none, `voltage_class_required` when it carries several.
7. **`export` takes no `--yes`**: it writes a new file it never overwrites (as `dsgrid-exchange convert`); `import`, `migrate` and `criteria clearance set` ride the typed-mutation plumbing (`--model` working copy revised in place or `--package` + `--out`; `--revision`; `--dry-run` xor `--yes`).
8. **Clearance criteria in the model.** `CriterionQuantity::ClearanceVoltageV` (all-weather rule, 30 000 V for MV), `CaseBindingRole::SurveyPointVerticalClearance` / `SurveyPointHorizontalClearance` bound to analysis cases at the named weather labels (condition final = after creep for both lists: REG rates clearances at 75 °C final, and the blow-out on the crept conductor is the larger sag), and the wire clearance line as the existing `MinimumVerticalClearanceM` rule at the class terrain floor (6 m MV) at the vertical case. CRI 94: `clearance_voltage`, `vertical_clear`, `phase_clear` (characterized as the horizontal survey-point list — the list that follows `vertical_clear`; the owner confirms in Criteria › Survey Point Clearances), `; Wire Clearance Line`, and the feature-code list after `m_iClearReportItemizeByWC` (rewritten to the model's live codes so PLS-CADD's report considers them). The Nyamagabe CRI's `phase_clear` names `High Temp.`, which is not a weather case of that file — a finding for the owner.
9. **Clearance report definitions** (PLS-CADD Terrain › Clearances, survey points): vertical = wire elevation above the point's top at the point's station for every point within the corridor half-width (the alignment's terrain corridor, else 12 m = the field file's `m_dMaxOffsetFromWire`); horizontal = plan distance between the point and the wire blown out toward the point at the horizontal case (exact load-plane catenary, both wind signs); vertical violation = available < required; horizontal violation = required > 0 and available < required; a vertical bust whose horizontal clearance satisfies a positive required horizontal is *questionable* (the FEA's "vert bust but horz ok") and is listed flagged, never dropped. An obstacle's top = surveyed z + h (`h=` in the description, else the code's default, flagged `obstacle_height_missing`); codes with an `h + k` / `H + k` rule take the height into the requirement. The lowest wire over a point governs. Verification level `proposal`.
10. **Cable condition at the cases.** The engine's transition rung cannot change cable condition for a cable without a characterized creep curve; such a section is evaluated at its reference condition and the report says so (`condition_transition_unavailable`, counted). A cable file whose cable-model row declares no nominal modulus (the field ACSR 70/12: `0 0`) now carries its own final-modulus row as the curve's final modulus under the polynomial's declared unit convention, so the temperature transition solves; not oracle-verified (contract 06).
11. **Old packages still read.** The feature-code table gained trailing nullable Arrow columns; the package verifier accepts the earlier schema generation's fingerprint and the decoder reads the missing columns as absent, so every 18 Sep package and working copy opens under the new build. Packages written by the new build carry the new columns; an older desktop build does not open them (the vendored WASM follows the kernel).
12. **The FEA is an engineering member**: `dsgrid-exchange convert` keeps it in the engineering projection (it was omitted as a utility file), imports it before the terrain, and resolves every survey point to its definition by the XYZ feature flag; the XYZ export writes the resolved code number as the flag and the rendered description as the text, and refuses (`edit offender`) a point whose code does not fit a byte (UNKNOWN 999) — a delivery has none.
13. **`criteria compare --project`** is deferred (no governed read in this cut); `criteria show` reports the one model's sets, weather cases and the maximum conductor temperature against 75 °C.
14. **MCP**: the seven verbs are one operator workflow and publish through the `grid-clearance` profile (like `grid-local-model`); the broad `grid` router's budget grows by seven.
15. **Spotting reads the survey-point vertical case (2026-09-21, server session).** `plan_optimum_spotting` proved clearance in the stringing basis's own sagging state against the one rule matching it, so a set filled by `criteria clearance set` (rule at the vertical case, none at the sag state) refused `clearance_authority_unresolved / no_matching_rule` on every Nyamagabe alignment. Now, when the requested criterion set binds `SurveyPointVerticalClearance`, the planner resolves the set's rule at that case (`resolve_clearance_requirement_at`), solves every span in that case's state through the report's own door (`clearance_report::case_state`, same condition fallback and limitation), and makes every corridor terrain point a clearance witness requiring what its feature code says (RV with the height rule above the point's top; an obstacle's top = z + h) — so the search itself keeps 8 m over a public road rather than a later report finding the crossing. The plan's basis carries `clearance_state` (case, weather, evaluated condition, solved constant, ruling span, limitations, witness counts). A set without the binding keeps the sagging-state path unchanged; the "second rule for another state" refusal applies to that path only, since the vertical case is by the set's declaration the deepest-sag state. Fixture tests: `tests/spotting.rs` (survey-point case as authority; 75 °C state solved, not the stringing constant; a 354 m span that clears 6 m of ground but not 8 m of road is split by the search).


## Refusals

`fea_version_unsupported` (names version), `feature_code_unknown_in_delivery` (999 count > 0 with `--deliver`), `voltage_class_unknown`, `clearance_case_missing` (weather label not in the set), `obstacle_height_missing` (report warning, not refusal), `standard_digest_mismatch` (JSON edited outside the owner's build).
