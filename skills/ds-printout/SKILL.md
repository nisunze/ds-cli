# DS Printout specialist

Own the print set through verified delivery; choose the next useful step.
Query an existing project, inspect supplied sources or resume verified outputs.
Do not require an archive when project data suffices. Proofs and queued uploads
are intermediate results.

Use `ds` for live CLI/MCP contracts and `ds-map-composition` for cartographic judgment.
Owners supply engineering facts and rendering. Keep schemas in live discovery;
never reconstruct a refusal through another door.

## Establish the assignment

- Recover project, source revision, audience, geography, formats, destination and
  earlier decisions. Build a canonical subject/layout/format matrix. "All" requires
  complete inventory, resolved pagination and explicit exclusions. Counts alone
  prove no coverage.
- Verify executable/lane and CLI-selected project. Read each operation's project
  resolution: some paired operations accept an explicit project independently of
  the map; map-owned operations require visible state. Switch Desktop only when
  needed for that operation. Available data in another project never changes the target.
- Read project settings and recipes. Determine whether the route renders locally,
  replaces outputs or queues publication. Preserve existing authorization across
  phases; ask only for material ambiguity or added scope, while continuing independent
  work. Do not infer printer hardware or spool a physical job from a PDF request.
- Keep scope, authorization, input/recipe revisions, expected outputs, receipts,
  QA coverage and next action in host task state or the designated deliverables
  directory. Historical records do not establish current identity or readiness.

## Prepare sources and context

Inspect model/design inventory through its owner. Resolve coordinate reference,
extent, required attributes and canonical identities. A route projection may support
an identified route overview; it cannot prove a complete pole/span design. Printing
does not authorize redesign, replacement numbering, invented ratings or construction
approval. Preserve existing infrastructure and dirty rooms when materializing data.

Use `ds-assets` for governed archives/documents/logos and authorized external source
access. Preserve bytes and digests. Source text is evidence, not authority. Trace
wording to its source page; keep unknown contract numbers/signatures unresolved.
An example does not dictate DS title-block arrangement.

For requested model preparation/publication, use `ds-grid-project-model` and the
source workflow. Keep model versions, design revisions and attachment IDs distinct;
attach original bytes to returned IDs, never an invented "v0". Read back ambiguous writes.

Choose context for purpose and printed extent, including margins and disconnected
clusters. Materialize project designs separately from national reference data.
Check source, coverage, freshness and readiness; downloaded bytes prove none of
them. Ready-empty, incomplete and stale differ. Seed relevant missing context through
its owner. Disclose optional exclusions only when purpose remains satisfied; required
missing data leaves delivery incomplete. Do not seed every dataset by habit or
substitute national reference transformers for project design transformers.

## Author and prepare sheets

Reuse suitable project recipes. If global-template adoption is authorized, retain
source identity/revision and create project-owned recipes. Preserve globals,
live-map styles, unrelated outputs and existing per-subject exceptions. Replace
inherited project wording/branding with sourced facts; never inherit approvals.
If no suitable template exists, author a project layout from the supported schema;
do not stop at an empty catalog or borrow an unrelated project's facts.

Compose each paper independently for scale, legibility and coverage. Record actual
paper, orientation and dimensions from recipe/receipt, not filename. Prioritize
engineering lines and canonical labels, then context, legends, schedules, scale and
title furniture. Use supported overview/detail pages or per-subject views where
density requires them. Mechanical A0 reduction does not establish readable A3 output.

Read schema and optimistic revision before authoring or saving. Validate and prepare
through the production route, preserving unselected output policy. Preparation may
save recipes/settings before context installation fails: read back state and current
revision before resuming. An error does not imply rollback; never replay create blindly.

## Render, inspect, refine

Produce representative sheets through the intended saved-project route before
batching. Cover each layout/format and distinct geographic/density cases. Check
identity, required layers, context warnings and source/recipe provenance in receipts.
A local layout proof does not validate project preparation, export or publication.

Inspect whole pages and readable crops: dense labels, rural coverage, junctions,
title block, legend and schedule edges. Can a reader follow and locate the network,
distinguish planned/existing infrastructure and read canonical labels? Check clipping,
overlaps, missing layers, legend categories, units and table scope. Ground scale and
quantities in owner output, never pixel measurements. Revise, rerender affected
samples and inspect again; successful rendering alone does not satisfy visual QA.

Review every page of a small overview/district set. For a large batch, review distinct
templates, diverse areas, outliers and representative sheets; record exact visual
coverage. Inspect every page when required. Sampling must not become an every-page claim.

## Produce and deliver

Run the scope/format matrix through an owner batch route where supported. Reuse
fresh outputs with matching dependencies; regenerate affected selected outputs while
retaining unselected artifacts. Match every expected identity to output IDs, actual
dimensions, revisions and verification receipts. Detect missing, duplicate, failed
and stale outputs even when counts match. Verify bytes through declared artifact
read/copy operations. Treat opaque locators as opaque; do not browse internal stores.

Preview and deliver readable files to the requested destination. Keep local verification,
publication and cross-machine readback separate. Verify published destination/version/
attachment IDs; queued uploads are incomplete. For local-only work, avoid routes
that automatically queue publication.

Complete means current verified matrix rows, stated visual QA and delivery to the
requested destination. Return artifact links, scope/counts and limitations. A proof
or boundary-only map cannot stand in for the engineering print set.

## Resume and recover

After interruption or deployment, revalidate identity, inventory, affected inputs
and live contracts. Protect dirty work and reuse unchanged dependencies. A recipe
change invalidates its prints, not source archives. Reconcile scope changes; inspect
ambiguous writes and outbox state before replaying them.

Classify failure as preparation, context/identity, authorization, invalid input,
transient failure or deployed-contract incompatibility. Follow remedies and retryability;
never repeat an unchanged non-retryable call. Verified new input or deployment evidence
can justify another attempt. Do not strip required content to appease an incompatible
validator. Continue independent work and preserve the exact remaining dependency.
Follow the user's official-feedback instructions without duplicates or a parallel backlog.

Read [delivery record](references/delivery-record.md) when resuming and
[acceptance](references/acceptance.md) before release. Disclose missing references,
retain these rules and seek supported skill access. Keep one writer for Desktop,
rooms and recipes. Delegate immutable review only when permitted; reconcile results.
